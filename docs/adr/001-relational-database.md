# ADR-001: Relational database of record

## Problem

The system needs an authoritative store for users, cases, evidence metadata, claims, reviews, and audit
events — the source of truth everything else (the graph projection, reports) is rebuilt from.

## Options considered

- **SQLite only** — zero install, but no real concurrent-write story and not what a multi-user deployment
  would run.
- **PostgreSQL only** — matches the target architecture, but forces every contributor and CI run to stand
  up a database server before the test suite works at all.
- **SQLite by default, PostgreSQL when configured** — `DRISHTI_DATABASE_URL` selects the backend; the same
  SQLAlchemy models and Alembic migrations apply to both.

## Decision

SQLite by default (zero-install dev/test loop), real PostgreSQL when `DRISHTI_DATABASE_URL` is set to a
`postgresql+psycopg2://` URL. `apps/api/app/db.py::init_db()` uses `create_all` only for the SQLite fast
path; every other URL applies the real Alembic migration in `apps/api/migrations/`.

## Reason

A contributor should be able to `git clone` and run the test suite in seconds with no external services —
that requirement doesn't go away just because production also needs Postgres. Keeping one model/schema
that runs against both (rather than a SQLite-only test suite and a separately-tested Postgres path) means
the same code and the same migration are what actually gets verified in both places.

## Trade-offs

SQLite's weaker concurrency and locking semantics mean the default path is not representative of
production load behavior — a bug that only appears under concurrent writes would not surface in the fast
test loop. This is accepted because the *full* suite is also run against real Postgres (see below), not
only the fast path.

## Security implications

No credentials in the SQLite path (a local file). Postgres credentials come from
`DRISHTI_DATABASE_URL`/environment, never hardcoded (`.env.example` documents the variable, `.env` itself
is gitignored).

## Performance implications

Not benchmarked at scale in this repo (`docs/context.md`'s own release-gate language: performance testing
is Roadmap, not claimed done). SQLite is adequate for the single-machine demo; Postgres is what a real
concurrent-user deployment needs.

## Migration

`apps/api/migrations/versions/96ad003ca363_initial_schema.py` — autogenerated from the live SQLAlchemy
models against a real Postgres instance, then hand-reviewed. `make db-upgrade` applies it.

## Rollback

Unset `DRISHTI_DATABASE_URL` to fall back to SQLite; no code change needed either direction since both
paths share the same models.

## Verification

Live-verified (`TASK_BOARD.md` Phase 1 and Phase 7): full `apps/api/app/tests` suite run against a real
PostgreSQL 16 instance in Docker, 27/27 passing, repeated 3+ consecutive times for stability. A real
test-isolation bug was found this way (session fixture didn't reset schema between runs against a
*persistent* database — invisible against a throwaway SQLite tempfile) and fixed in `conftest.py`.
